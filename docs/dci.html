1. What the DCI is, and the problem it solves

ACME Networks sells the VPN service; the branches are its customers. ACME has acquired a company, and that company arrives with its own network — including addresses ACME already uses. The lab models the whole situation: a data-centre interconnect (DCI) hangs off one headend, the acquired company's edge router (ACME-acquisition) hangs off the DCI, and the two sides collide on 1001 prefixes at once:

CollisionOn the ACME sideOn the acquired company's side
A branch LAN, reused verbatim192.168.12.0/24 — branch 1's LAN; host-spoke1 is 192.168.12.2192.168.12.0/24 — a server on Loopback2, also 192.168.12.2
A thousand /24s (the scale set)10.128.0.0/24 … 10.131.231.0/24, ACME holds .1 in eachthe same thousand prefixes, the acquired company holds .2 in each

Nothing is renumbered. The DCI hides the collision with a twice-NAT, keeps each side's copy on its own side with a route filter, and doctors DNS answers in flight so that a name resolved across the DCI returns an address the asker can actually reach. The whole arrangement is modelled in Nautobot, rendered by the same Network-as-Code pipeline and Golden Config template as every other router, and proven by twelve Robot tests.

Why it is interesting. The scale lands on the NAT, not on the routing table: the DCI carries 2002 static translations while BGP carries three aggregates. A thousand interfaces per side would be absurd, so each side holds its thousand addresses as secondary addresses on one loopback.

Both links are cables between router ports in Nautobot — no firewall between them — and neither router carries a tunnel, a crypto profile or a keyring: the encryption stops at the headends. The acquired company's overlapping prefix lives in its own Nautobot namespace (acquisition), because it is not ACME's address space.

3. The path a branch takes to the acquisition

A branch has no special knowledge of the DCI. It learns the acquisition's prefixes over its IPsec tunnels like any other destination, and the path runs branch → tunnel → headend(s) → west-headend → DCI → acquisition. Taken live from host-spoke1:

host-spoke1 $ traceroute -n 192.168.30.2            # the acquisition's LAN host
 1  192.168.12.1   0.407 ms     spoke1, the branch's own gateway
 2  172.17.4.1     1.508 ms     central-headend, over Tunnel4 (IPsec VTI)
 3  172.17.5.2     1.430 ms     spoke2 — the branch mesh is the transit between headends
 4  172.17.9.1     4.226 ms     west-headend, over Tunnel9
 5  *                           the DCI does not answer this probe — see the note below
 6  100.64.21.2    4.056 ms     ACME-acquisition
 7  192.168.30.2   4.383 ms     host-acquisition

From a host that is not inside the overlapping prefix the same path is three hops shorter and the DCI answers normally:

host-west $ traceroute -n 192.168.30.2
 1  192.168.16.1   0.005 ms     west-headend
 2  100.64.20.2    0.523 ms     DCI
 3  100.64.21.2    1.201 ms     ACME-acquisition
 4  192.168.30.2   1.873 ms
Why hop 5 is silent — and why that is correct. The DCI's own routing table resolves 192.168.12.0/24 towards the acquired company (B 192.168.12.0/24 via 100.64.21.2), because on the DCI that prefix belongs to the acquisition — ACME's copy is filtered out. A TTL-expired message the DCI generates for host-spoke1 would therefore be sent to the acquisition's server instead of back to the branch, so it never arrives. Hosts inside the overlapping prefix cannot ping the DCI itself either (host-west can). Traffic through the DCI is unaffected: that is translated, and translation happens before the DCI's own routing decision matters.

Neither end ever sees the other's real address, and neither end needs a route for it.

The filter that keeps each copy at home

DCI # show running-config | include OVERLAP|NO-OVERLAP
ip prefix-list OVERLAP description prefixes that exist on both sides of the DCI: translated, not advertised
ip prefix-list OVERLAP seq 5  permit 192.168.12.0/24
ip prefix-list OVERLAP seq 10 permit 10.128.0.0/14
route-map NO-OVERLAP deny 10       match ip address prefix-list OVERLAP
route-map NO-OVERLAP permit 20     everything else is advertised normally
  neighbor 100.64.20.1 route-map NO-OVERLAP in     ACME's copy never enters the DCI
  neighbor 100.64.20.1 route-map NO-OVERLAP out    the acquisition's copy never leaves towards ACME
  neighbor 100.64.21.2 route-map NO-OVERLAP out    ACME's copy never leaves towards the acquisition

Each router therefore keeps exactly one path per prefix — its own. What crosses the DCI instead is the translated range, which the DCI originates itself, together with the two static routes the translation needs:

DCI # show running-config | include ^ip route
ip route 100.96.0.0   255.252.0.0 Null0        name nat-inside-global    translated before the routing lookup
ip route 172.31.12.0  255.255.255.0 Null0      name nat-inside-global
ip route 100.100.0.0  255.252.0.0 100.64.20.1 name nat-outside-local    routed before the translation
ip route 172.30.12.0  255.255.255.0 100.64.20.1 name nat-outside-local
Read the two halves. A packet from ACME to 100.96.x.y is translated first and then routed, so that range only needs to exist — a Null0 route is enough, and it is what the DCI advertises to ACME. A packet from the acquisition to 100.100.x.y is routed first and translated after, so the DCI needs a real next hop towards ACME. ACME itself never learns 100.100.0.0/14: by the time a packet reaches west-headend its destination is already the real 10.128.x.1.

5. How the NAT is set up

Two interface roles and two kinds of static translation — the pair that IOS calls twice NAT, because both the source and the destination of a flow are rewritten:

TermIn this labConfigured as
inside localthe acquired company's real address, e.g. 10.128.7.2ip nat inside source static network 10.128.N.0 100.96.N.0 /24
inside globalthe same host as ACME sees it: 100.96.7.2
outside globalACME's real address, e.g. 10.128.7.1 (or 192.168.12.2)ip nat outside source static network 10.128.N.0 100.100.N.0 /24
outside localthe same host as the acquisition sees it: 100.100.7.1 (or 172.30.12.2)

Where the thousand come from

One scale block in lab-intent.json generates every line above — the statics, the loopback addresses on both sides, the aggregates and the DNS records:

Two platform limits worth knowing. IOS-XE's CLI RPC rejects a payload of this size (“invalid value for: config-clis … has a bad length/size” at roughly two thousand lines), so the renderer splits every CLI template into 400-line chunks, repeating the section header where the lines only make sense inside one. And a CLI template never removes the lines of a previous version — shrinking a scale set means removing the old statements explicitly.

6. How DNS is fixed up

Each side answers for its own zone, with its own copies of the overlapping addresses. A resolver on the far side of the DCI would therefore be handed an address that means something completely different at home — unless the NAT rewrites the answer. That rewrite is the DNS application-level gateway built into IOS NAT: when a DNS reply crosses a NAT boundary, the A records inside the payload are translated with the same statics as the packet header.

The reverse direction works the same way and is easiest to see from the router itself, which resolves and pings in one command:

ACME-acquisition # ping svc7.acme.local source 10.128.7.2
Sending 2, 100-byte ICMP Echos to 100.100.7.1, timeout is 2 seconds:   the record says 10.128.7.1
Packet sent with a source address of 10.128.7.2
!!
Success rate is 100 percent (2/2), round-trip min/avg/max = 1/2/3 ms
The source address is the part that is easy to get wrong. The ALG only rewrites a payload on a flow the NAT is already translating. host-spoke1 sits in 192.168.12.0/24 — the single hand-written overlap — so its queries leave as 172.30.12.2 and the answer comes back doctored; ACME-acquisition sources its own queries from Loopback2 for exactly the same reason. A host outside any overlap would receive the raw 10.131.9.2 and have nowhere to send it. Setting "dns_fixup": false in the intent renders the opposite: no-payload on the statics and no ip nat service dns tcp/udp.

How the two scale tests actually sweep

  1. The expected values are computed from the intent, not hard-coded: intent.nat_scale() expands the scale block into 1000 entries, each with its prefix, its inside-global and outside-local forms, and each side's address (acquisition_as_acme_sees_it = 100.96.N.2, acme_as_acquisition_sees_it = 100.100.N.1). The same function feeds the renderer, so the test and the device are computed from one source.
  2. The NAT sweep ships the thousand target addresses to host-spoke1 as one list and pings them forty at a time (xargs -P 40): about five seconds for all thousand, against minutes if run serially. The test asserts reached 1000/1000 and prints any address that failed.
  3. The DNS sweep ships a thousand name=expected pairs, resolves each with nslookup -type=a (filtering out busybox's server line and its AAAA “No answer” noise), compares the answer to the address the NAT should have produced and then pings it — so a name that resolves to something unreachable fails. The assertion is resolved+reached 1000/1000.
  4. The reverse direction is checked from the router, where there is no busybox: ping svcN.acme.local source 10.128.N.2 must both resolve to the outside-local form and succeed.
  5. The counters are read independently: show ip nat statistics must show exactly two static translations per overlapping prefix and zero drops, and show ip route must contain the three aggregates and nothing per-prefix.
