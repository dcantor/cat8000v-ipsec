3. The intent document

lab-intent.json is the single input to every workflow. It is created once from lab.conf (./lab.sh intent init) and afterwards only written by the portal (deploy) or by the spoke/hub/remove steps. intent.load() upgrades older documents in place (tunnels gain a hub, spokes gain a psk, devices gain region/site).

4. Workflow: Deploy / Dry run

Triggered by Deploy configuration (mode deploy) or Dry run (mode plan) on the Provision page, or POST /api/runs. Steps: validate → save → nautobot → render → plan → apply → golden → test (plan stops after plan).

sequenceDiagram
  autonumber
  participant B as Browser
  participant P as Portal (run thread)
  participant I as lab-intent.json
  participant S as seed.py
  participant NB as Nautobot
  participant R as render_nac.py
  B->>P: POST /api/runs {mode, intent, options}
  P->>P: intent.validate() → 422 with problems if invalid
  P-->>B: run id (queued)
  loop every 2 s
    B->>P: GET /api/runs/{id}?since=N
    P-->>B: steps, new log lines, tests
  end
  P->>I: save intent (+ copy to runs/{id}.intent.json)
  P->>S: ./lab.sh nautobot seed
  S->>NB: REST get / create / update (idempotent), GraphQL reads
  S-->>P: seed complete: N changes
  P->>R: ./lab.sh nautobot render
  R->>NB: POST /api/graphql (saved query)
  R->>I: read per-spoke PSKs
  R-->>P: devices.nac.yaml + device_groups.nac.yaml written

5. Workflow: Add a spoke

The wizard (3 steps) ends in POST /api/runs {mode: "spoke", spoke: SpokeSpec}. Steps: spoke_validate → spoke_labconf → spoke_vm → spoke_bootstrap → spoke_onboard → spoke_intent → nautobot → render → plan → apply → golden → test.

sequenceDiagram
  autonumber
  participant B as Browser (wizard)
  participant P as Portal
  participant SP as spokes.py
  participant LC as lab.conf / nodes
  participant LV as libvirt
  B->>P: GET /api/spokes/suggest?region=West
  P->>SP: suggest(): hostname, mgmt IP, node idx, console port, router-id, LAN, AS, site, PSK · nearest 2 headends · per-headend link allocation
  P-->>B: SpokeSpec + context (headends, free ports, capacity)
  B->>P: POST /api/spokes/validate {spoke} (each wizard step)
  P-->>B: problems[] · hub_changes (what each headend and the spoke get)
  B->>P: POST /api/runs {mode: spoke, spoke, options}
  P->>SP: validate again (server side)
  P->>LC: add_to_lab_conf (arrays, LINKS, TUNNELS) · write_day0 from nodes/_template
  P->>LV: ./lab.sh up spoke — overlay disk, CVAC ISO, domain XML, start

Phase 2 — bring the router up and into the model

sequenceDiagram
  autonumber
  participant P as Portal
  participant C as Router console (TCP)
  participant NB as Nautobot
  participant I as lab-intent.json
  P->>C: ./lab.sh bootstrap spoke — wait for the prompt (≤ 30 min), push day-0 + RSA key
  P->>C: show version → license level?
  alt license level not active
    P->>C: write memory · reload · wait again
  end
  P->>C: poll RESTCONF until 200
  P->>NB: ./lab.sh nautobot onboard mgmt_ip (job Sync Devices From Network)
  NB-->>P: device with model, serial, platform, primary IP
  P->>I: add_to_intent: device (+ region / site / PSK), one link and one tunnel per headend
  Note over P,I: then the Deploy pipeline: seed → render → plan → apply (headends + spoke in one apply) → Golden Config → tests
Every step is idempotent so a failed run can be resumed: spoke_labconf skips if the name is already in lab.conf, lab.sh up reports "already running", spoke_intent skips if the device is already in the intent.

6. Workflow: Add a headend

POST /api/runs {mode: "hub", hub: HubSpec} (from GET /api/hubs/suggest). Same shape as a spoke, with two differences: the new headend gets a link + tunnel to every existing spoke (spokes.hub_links(), each spoke's next free WAN port), and because a link is anchored on the headend's UDP ports, each existing spoke's libvirt definition changes — the run re-defines and reboots each spoke (down / rebuild / up) and waits for them after the headend's bootstrap.

flowchart TD
  A["hub_validate: validate identity; hub_links → one link per spoke"] --> B{"every spoke has a free WAN port?"}
  B -- no --> X["fail: raise SPOKE_PORTS in lab.conf"]
  B -- yes --> C["hub_labconf: lab.conf + day-0; for each spoke: down → rebuild → up"]
  C --> D["hub_vm: define + start the headend"]
  D --> E["hub_bootstrap: console day-0, license reload, RESTCONF; wait for rebooted spokes"]
  E --> F["hub_onboard: Sync Devices From Network"]
  F --> G["hub_intent: device + links + tunnels"]
  G --> H["seed → render → plan → apply → golden → tests"]

7. Workflow: Remove a spoke

Remove… on a spoke row → GET /api/spokes/{name}/removal (plan dialog) → POST /api/runs {mode: "remove", spoke: {name}}. Steps: rm_validate → rm_down → rm_nautobot → rm_intent → nautobot → render → rm_state → plan → apply → rm_vm → golden → test.

sequenceDiagram
  autonumber
  participant P as Portal
  participant LV as libvirt
  participant NB as Nautobot
  participant I as lab-intent.json / lab.conf
  participant TF as Terraform
  participant RT as Headends
  P->>LV: ./lab.sh down spoke (config saved, powered off)
  P->>NB: delete BGP peerings + routing instance (they reference tunnel addresses)
  P->>NB: delete VPN tunnels, both endpoints, headend TunnelN interfaces + addresses
  P->>NB: delete the spoke's addresses and cables, the device (cascades interfaces)
  P->>NB: delete every address inside its prefixes, then the prefixes · unused AS
  P->>I: remove device/links/tunnels · remove lab.conf entries (regex)
  P->>NB: seed (headend ports become unwired/disabled · stale tunnels gone)
  P->>TF: render · terraform state rm every resource keyed "spoke/…" (router no longer exists)
  P->>TF: plan → apply
  TF->>RT: DELETE TunnelN, BGP neighbour, WAN address · PATCH port shutdown
  P->>LV: ./lab.sh clean spoke (undefine, delete disk + nodes/spoke) — or down only if keep-disk
  Note over P,RT: Golden Config + tests as usual

8. Workflow: Resume, tests, inventory

Resume

flowchart TD
  A["POST /api/runs/{id}/resume"] --> B{"status failed or interrupted?"}
  B -- no --> E["409"]
  B -- yes --> C{"another run active?"}
  C -- yes --> E2["409"]
  C -- no --> D["new Run same mode/spec; steps that succeeded are copied as success; execute skips them"]
  D --> F["first non-success step re-runs; all later steps run"]

On start-up the portal marks runs found "running" as interrupted (running step → failed, pending → skipped) so they are resumable. webapp/restart.sh refuses to restart while a run is active.

Inventory refresh

flowchart TD
  A["GET /api/vpn-inventory"] --> B{"cache younger than 30 s and not refresh?"}
  B -- yes --> Z["return cached"]
  B -- no --> C["GraphQL: vpns → tunnels → endpoints → devices, profile"]
  C --> D["for each headend in parallel: SSH show commands"]
  D --> E["join per tunnel on far source IP / tunnel interface / tunnel IP"]
  E --> F["health: IKE READY ∧ VTI up ∧ BGP Established → up; IKE READY only → degraded; else down"]
  F --> G["capacity per headend: tunnels / cf_vpn_tunnel_capacity and (tunnels × bandwidth_per_tunnel_mbps) / cf_firewall_bandwidth_mbps of its firewall; live control-plane CPU / warning threshold (show platform resources); aggregate = tightest of the three, effective free slots (0 when CPU ≥ threshold)"]
  G --> Z

Tests (mode test, or the last step of every run)

tests/run.sh creates results/<date>_<time>/, captures every router's running/startup config (configs/pre-run), runs the six suites, captures again (configs/post-run) and diffs; results/latest points at the newest run. The portal parses output.xml into the per-suite report shown in the UI and serves report.html/log.html/backups under /results/.

9. Decision trees: intent validation (intent.validate)

flowchart TD
  A["intent"] --> B{"hostnames unique; letters/digits/hyphen, start with a letter, ≤ 63 chars?"}
  B --> C{"each device: mgmt_ip and router_id are IPv4, LAN a strict /24, ASN 1..4294967295"}
  C --> D{"≥ 1 hub-role device?"}
  D --> E{"router-ids unique · LANs unique"}
  E --> F{"every VM in lab.conf present by mgmt IP with the same role? no unknown mgmt IPs?"}

flowchart TD
  G{"links == physical wiring, translated to the current hostnames?"} --> H{"link prefixes strict /30, none reused"}
  H --> I{"tunnel ids unique · one tunnel per hub/spoke pair · hub is a hub · spoke is a spoke · a link exists between them"}
  I --> J{"every spoke has ≥ 1 tunnel"}
  J --> K{"tunnels per hub ≤ capacity.tunnels_per_headend and tunnels × bandwidth_per_tunnel_mbps ≤ firewall bandwidth_mbps"}
  K --> L{"tunnel prefixes strict /30, unused"}

flowchart TD
  M{"profile: IKE enc ∈ AES-CBC/GCM set, integrity ∈ SHA1/256/384/512/MD5, DH ∈ 14/19/20/21/24; IPsec likewise; DPD 10..3600 s × 2..60"} --> N{"regions non-empty; each device region ∈ regions; site name valid; a site not in two regions"}
  N --> O{"spokes: PSK 8..64 chars of letters/digits/_.-"}
  O --> P{"VPN name and profile name: letters/digits/_-, up to 40 chars"}
  P --> Z["problems list — every failed check adds one line; empty = valid"]

All checks run; the caller gets the full list. The pipeline refuses to start (HTTP 422) or fails its first step on any problem.

Why the crypto-profiles-first apply: the NAC module has no dependency from iosxe_interface_tunnel to iosxe_crypto_ipsec_profile, and IOS-XE refuses a tunnel whose tunnel protection ipsec profile does not exist yet — on a brand-new router the first full apply could push the VTI before its profile. Why the convergence apply: after an interface deletion or a reload IOS-XE re-syncs its YANG datastore and elides default values (transform-set key size, SSH defaults); one re-assert fixes it.
