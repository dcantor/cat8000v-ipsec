1. Purpose, scope and system context

The system provides a managed hub-and-spoke IPsec VPN service: a provider (ACME Networks) operates regional headends; each customer branch is a Catalyst 8000v spoke with IPsec VTIs to two or more headends and eBGP over them, so every site LAN reaches every other site LAN through the encrypted tunnels, and reaches the internet through the nearest headend's firewall. Everything about the service is described once (the intent), stored in Nautobot as the source of truth, rendered into Network-as-Code data and pushed to the routers by Terraform, checked by Golden Config compliance, proven by Robot Framework tests, and operated from a web portal with a REST API. The lab realises this on one KVM host with libvirt VMs, but the requirements describe the service, not the host.

12. Data-centre interconnect: an acquired company, overlapping addresses, NAT and DNS

IDPrioRequirementAcceptance criteria
DCI-01MUSTA data-centre interconnect hangs off one headend (west-headend Gi3 → DCI → ACME-acquisition) on plain routed /30s with no IPsec: ACME owns the DCI (tenant ACME Networks, role vpn-dci), the acquired company is a customer tenant of its own on a partner-edge router. Devices, cables, prefixes, peerings and tenants are modelled in Nautobot and rendered by the same NaC pipeline and Golden Config template as everything else.suite 12 "The DCI chain is modelled in Nautobot…", "The interconnect links are up … no IPsec anywhere on them"
DCI-02MUSTeBGP per hop (65206 ↔ 65208 ↔ 65209) from the same nautobot-bgp-models peerings the tunnels use; the acquisition originates its site LAN and a service prefix on a loopback, which every branch learns through one of its headends and can reach from its own LAN address; the host behind the acquisition joins the ping mesh and breaks out to the internet through the headend.suite 12 "eBGP is Established on every hop…", "The acquisition originates its prefixes…", "A branch reaches the acquisition's LAN…", "The host behind the acquisition is in the mesh…"
DCI-03MUSTOverlapping address space is translated, not renumbered: the acquired company keeps a prefix ACME already uses (its own Nautobot namespace), and the DCI runs a twice-NAT — ip nat inside source static network (inside local → inside global) and ip nat outside source static network (outside global → outside local) — with ip nat inside / outside on the two interconnect ports. A prefix-list OVERLAP and route-map NO-OVERLAP filter the colliding prefix in and out towards ACME and out towards the acquisition, and the translated ranges are advertised instead (a Null0 route for the inside-global range, a route towards ACME for the outside-local one).suite 12 "The overlapping prefix exists on both sides … neither side learns the other's copy", "The DCI translates in both directions…"
DCI-04MUSTDNS fix-up in both directions: each side answers for its own zone (ip dns server + ip host records rendered from the intent), the far side resolves through the DCI from an address the NAT translates, and the ALG rewrites the A records in flight so what a client resolves is what it can reach. A LAN host's resolver comes from the intent (dns_client, written by cloud-init; the instance-id follows a hash of the seed so a changed resolver is applied on the next boot).suite 12 "DNS is fixed up on the way through the NAT…", "DNS fix-up scales and works from either side…" and "The fix-up is visible on the wire…" — a packet capture on both of the DCI's interfaces shows the same answer carrying the real address inside and its translated form outside (tools/dns_capture.py, .pcap kept with the run)
DCI-05MUSTScale: a scale block expands to 1000 overlapping /24s on both sides — 2002 static translations on the DCI — while BGP carries only three aggregates; each side holds its thousand addresses as secondary addresses on one loopback, and the renderer splits CLI templates into 400-line chunks (IOS-XE's CLI RPC rejects a larger payload). Each zone carries 1000 records over the same set.suite 12 "NAT scales: a thousand overlapping prefixes…" (reached 1000/1000, no drops, aggregates only) and "DNS fix-up scales…" (resolved+reached 1000/1000)
DCI-06MUSTThe NAT and the DNS are under configuration compliance like everything else: two Golden Config features (NAT (DCI), DNS) whose intended configuration is rendered from the same config context — including the full scale set — so a hand-edit anywhere in it shows up as drift.171/171 compliance rows compliant; suite 12 "Golden Config renders the DCI chain…"
DCI-07SHOULDThe interconnect is visible in the portal: the DCI and the acquisition appear on both topology views (dashed, as non-IPsec links) and in the Branches table with their tenant and design pattern.topology screenshots; suite 10 / suite 06

23. Constraints, assumptions and known limits

  • The iosxe provider's IKEv2 profile knows only pre-share authentication; rsa-sig, the certificate map and the trustpoint are pushed as a raw CLI template that depends on every native resource (so it always goes in the last apply stage). A CLI template's destroy does not revert lines; retiring a certificate removes the trustpoint and map, which makes IOS drop the dependent profile lines.
  • IOS-XE shuts a VTI whose protection profile is swapped and refuses deleting an in-use profile or keyring — hence the staged apply and the post-apply verification.
  • IOS-XE appends a route-map entry's description over RESTCONF instead of replacing it: a description whose text changes (it used to carry the internet-breakout preference rank, which a re-home changes) leaves the old line on the router and Golden Config reports drift. Rendered descriptions are therefore stable per object; the rank lives in set local-preference, which the provider does replace. Suite 11 asserts one description per route-map entry.
  • Nautobot 3.2.4: a brand-new custom field drops values until it is saved a second time; the profile ↔ policy assignment endpoints 500 on POST (worked around); a location's description is limited to 255 characters.
  • Golden Config compliance needs parseable backups: a multi-line banner breaks hier_config for that device.
  • IOS-XE's CLI RPC rejects a very large payload (bad length/size at roughly two thousand lines): the renderer splits every CLI template into 400-line chunks, repeating the section header. A CLI template never removes the lines of a previous version, so shrinking a scale set means removing the old statements explicitly.
  • The Alpine LAN hosts route 10.0.0.0/8 out of their OOB interface, so anything they must reach through the lab is addressed outside that range: the translated ranges live in 100.96.0.0/11 and the acquired company's real prefixes (10.128.0.0/14) are only ever reached through the NAT.
  • VyOS static routes have no description leaf; the breakout uplink uses DHCP on the libvirt NAT network.
  • Pre-shared keys are kept in the intent (a git-tracked file in the lab); a production deployment would move them to a secret store — the portal already treats them as secrets everywhere else.
  • Customers are synthetic (deterministic fakes); the model, fields and filters are what a real CRM feed would fill.
  • Both labs on the host share one Nautobot and one NMS; their test suites must not run concurrently.
